# BobFull 개인 리팩토링 워크플로우

## 목적

팀 프로젝트 종료 후 개인 고도화에서는 단순히 코드를 고치는 것보다 근거를 남기며 이해하고 개선하는 과정을 우선한다.

한 번의 리팩토링 작업이 다음 결과로 이어지게 한다.

- GitHub Issue와 PR의 검증 기록
- 필요한 경우 트러블슈팅 원본
- 기술면접 대비용 Q&A
- 기술블로그 후보
- 포트폴리오 후보
- AI 활용 과정에서 Human이 내린 판단 기록

## 최우선 원칙

> AI가 작성하거나 제안한 핵심 코드라도 Human이 설명할 수 없으면 Merge하지 않는다.

추가 원칙:

- 한 Issue와 PR에는 하나의 주요 목적만 둔다.
- 리팩토링과 기능 추가, 성능 개선, 정책 변경을 가능한 한 분리한다.
- 테스트와 필요한 측정으로 회귀 여부를 확인한다.
- 의미 없는 수치는 억지로 만들지 않는다.
- API, DB, 비즈니스 정책 변경이 필요하면 별도 Issue로 분리한다.

## 전체 흐름

```text
0. BASELINE
   현재 상태 확인
        ↓
1. ISSUE
   문제, 범위, 고정 계약, 검증 방법 정의
        ↓
2. UNDERSTAND
   현재 코드 흐름과 위험 이해
        ↓
3. AI ANALYSIS
   대안, 테스트 포인트, 구현 초안 탐색
        ↓
4. HUMAN READY
   바꿀 것과 바꾸지 않을 것을 확인
        ↓
5. TEST SAFETY NET
   기존 동작 보호
        ↓
6. REFACTOR
   한 가지 목적만 변경
        ↓
7. VERIFY
   테스트, build, 필요한 지표 확인
        ↓
8. TROUBLESHOOTING GATE
   의미 있는 문제 해결이면 원본 기록
        ↓
9. DRAFT PR
   변경, 이유, 검증, AI 활용 기록
        ↓
10. AI SELF REVIEW
    최신 Diff 재검토
        ↓
11. UNDERSTANDING GATE
    AI가 쉬운 면접 Q&A 작성, Human은 읽고 이해 확인
        ↓
12. HUMAN MERGE
        ↓
13. OUTPUT
    Troubleshooting, Tech Blog, Interview, Portfolio 후보 판정
```

## 0. Baseline

리팩토링 전에 현재 상태를 먼저 남긴다.

- 관련 테스트 결과
- 전체 build 결과
- 필요한 JaCoCo 지표
- 필요한 SonarQube 지표
- 성능, 동시성, 정합성 문제라면 해당 문제의 재현 결과

모든 Issue에 모든 지표가 필요한 것은 아니다. 현재 작업의 목적과 직접 관련된 것만 사용한다.

## 1. Issue

리팩토링은 `.github/ISSUE_TEMPLATE/refactor.md`로 시작한다.

구현 전 최소한 다음을 확정한다.

- 무엇이 문제인지
- 첫 작업 범위
- 무엇은 바뀌면 안 되는지
- 어떤 방법으로 바꿀지
- 무엇으로 검증할지
- AI와 Human의 역할

## 2. Understand

AI에게 구현을 맡기기 전에 현재 코드를 먼저 이해한다.

필요한 항목:

- 요청 시작점
- 핵심 호출 흐름
- 트랜잭션 경계
- 상태 변경 위치
- 외부 I/O
- 의존 방향
- 변경 시 깨질 수 있는 동작

모든 항목을 시험처럼 답하게 하지는 않는다. 이번 변경과 직접 관련된 부분만 이해하면 된다.

## 3. AI Analysis

AI가 맡을 수 있는 것:

- 관련 코드 구조 분석
- 문제 후보와 원인 가설
- 해결 대안 비교
- 테스트 후보
- 리팩토링 코드 초안
- Diff Self Review
- 면접 질문과 답안 작성
- 트러블슈팅과 블로그 초안 구조화

Human이 책임질 것:

- 실제 문제가 맞는지 판단
- 도메인 정책
- 트랜잭션 경계
- API와 DB 계약
- 최종 구조 선택
- 테스트 결과 해석
- 최종 Merge

## 4. Human READY

코드 수정 전에는 아래 네 가지만 확인한다.

1. 무엇을 바꾸는가?
2. 무엇은 절대 바뀌면 안 되는가?
3. 어떤 방법으로 바꿀 것인가?
4. 무엇으로 검증할 것인가?

이미 Issue와 대화에서 결정된 내용은 다시 묻지 않는다. 결정이 필요한 항목만 Human에게 요청한다.

## 5. Test Safety Net

리팩토링 전 기존 동작을 보호할 테스트가 있는지 확인한다.

- 핵심 비즈니스 규칙
- 상태 전이
- 트랜잭션 rollback
- 동시성, 멱등성
- 외부 시스템 경계
- 정상, 실패, 경계 시나리오

필요한 최소 안전망만 보강한다.

## 6. Refactor

- 한 Issue에서 한 가지 목적만 변경한다.
- 기능 추가를 섞지 않는다.
- 의미 없는 패턴과 추상화를 추가하지 않는다.
- 기존 외부 동작을 유지한다.
- 범위가 커지면 별도 Issue로 분리한다.

## 7. Verify

기본 기준:

```text
관련 테스트 PASS
+ 전체 build PASS
+ 핵심 동작 확인
+ 필요한 SonarQube 또는 JaCoCo 비교
+ API, DB, 비즈니스 정책 회귀 없음
```

Before와 After는 가능한 한 동일한 조건으로 비교한다.

## 8. Troubleshooting Gate

모든 리팩토링을 트러블슈팅으로 포장하지 않는다.

다음 흐름이 실제로 존재할 때만 기록한다.

```text
문제 → 재현 → 원인 가설 → 확인 → 근본 원인 → 대안 비교 → 선택 → 구현 → 검증 → Before/After → 결과 → 한계
```

단순 주석 정리, 네이밍 변경, 포맷 정리는 보통 트러블슈팅 후보가 아니다.

## 9. PR

PR은 길게 쓰는 문서가 아니라 최종 검문소다.

최소한 다음만 남긴다.

- 무엇을 바꿨는지
- 왜 바꿨는지
- 무엇은 바꾸지 않았는지
- 어떻게 검증했는지
- 의미 있는 Before와 After
- AI가 한 일과 Human이 결정한 일
- 면접용 Q&A
- Output Gate

의미 없는 빈 섹션은 만들지 않는다.

## 10. AI Self Review

Draft PR 생성 후 최신 Head와 Diff를 다시 본다.

- Issue 범위 밖 변경
- 기능 회귀
- 트랜잭션과 정합성 문제
- 테스트 누락
- 과도한 추상화
- SonarQube 점수만 맞추는 부자연스러운 변경
- 설명하기 어려운 AI 생성 코드

BLOCKER와 MAJOR가 있으면 수정 후 다시 검증한다.

## 11. Understanding Gate

Merge 전에 Human에게 추상적인 서술형 질문지를 작성하게 하지 않는다.

AI가 해당 PR의 실제 변경을 기준으로 쉬운 질문 2~3개와 답안을 함께 작성한다.

예시:

- 이번에 무엇을 바꿨나요?
- 왜 이 방법을 선택했나요?
- 안전하게 바뀌었다는 것을 어떻게 확인했나요?
- 필요하면 핵심 Java/Spring 개념은 무엇인가요?

답안은 실제 코드, Issue, 테스트, 측정 결과에 근거한다. 모르는 내용은 임의로 채우지 않는다.

Human은 다음만 확인한다.

1. 답안 내용이 실제 변경과 맞는가?
2. 코드 없이도 이 정도는 설명할 수 있는가?
3. 이해되지 않는 AI 생성 핵심 코드가 없는가?

틀린 내용은 수정하고 이해가 안 되는 부분만 다시 학습한다. 별도 장문 답변은 요구하지 않는다.

## 12. Human Merge

AI는 최종 Merge하지 않는다. Human이 PR 내용과 Q&A를 확인한 뒤 직접 Merge한다.

## 13. Output Gate

작업 종료 시 다음을 판정한다.

### Troubleshooting

실제 문제 재현, 원인 분석, 해결 판단, 검증 과정이 명확할 때만 `YES`.

### Tech Blog

명확한 문제, 원인 분석, 대안 비교, 기술적 판단, 객관적 검증, 재사용 가치, 면접 가치 중 의미 있는 요소가 충분할 때만 `YES`.

### Interview Note

핵심 개념, 선택 이유, 검증 방법, 한계를 짧은 Q&A 형태로 남긴다.

### Portfolio

단순 코드 정리가 아니라 문제 해결 능력과 기술적 판단을 보여줄 수 있을 때만 `YES`.

## 현재 BobFull 적용 순서

```text
SonarQube + JaCoCo Before 기준선 확정
→ 테스트 안전망 점검
→ 도메인과 패키지 경계
→ 클래스와 메서드 책임 분리
→ 중복, 네이밍, 조건식 정리
→ SonarQube 잔여 Issue 선별 처리
→ 동일 조건 최종 재측정
→ 대표 Troubleshooting, Tech Blog, Interview, Portfolio 산출물 정리
```

Baseline Issue #2는 완료된 공통 기준선으로 사용한다.
